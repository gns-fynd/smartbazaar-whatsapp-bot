# Jio Commerce API map (documented contract vs live evidence)

This is a research map for the proposed agent tools. Paths and fields below are from the official Storefront REST documentation; they are not proof that the same routes, scopes, or schemas are enabled for the tested JioMart account.

Sources: [Storefront client libraries](https://partners-doc.jiocommerce.io/help/docs/sdk/latest/application/client-libraries), [catalog](https://partners-doc.jiocommerce.io/help/docs/sdk/latest/application/catalog), [order](https://partners-doc.jiocommerce.io/help/docs/sdk/latest/application/order), [payment](https://partners-doc.jiocommerce.io/help/docs/sdk/latest/application/payment), [cart object](https://partners-doc.jiocommerce.io/help/docs/sdk/latest/graphql/application/cart/objects/Cart), and [platform client libraries](https://partners-doc.jiocommerce.io/help/docs/sdk/latest/platform/client-libraries).

## Customer history contract

`GET /service/application/order/v1.0/orders` (`getOrders`) documents query filters `status`, `fulfillment_mode`, `statuses` (comma-separated), `page_no` (default 1), `page_size` (default 10), `from_date`, `to_date`, `start_date`, `end_date`, and `custom_meta`. The documented response is `OrderList` with `page.type`, `page.item_total`, `page.current`, `page.size`, `page.has_next`, and `items[]` of `OrderSchema`.

`GET /service/application/order/v1.0/orders/{order_id}` (`getOrderById`) accepts `order_id` and optional `allow_inactive`. The docs describe an order as containing one or more shipments; each shipment contains zero or more bags. Documented nested fields include order identifiers and timestamps (`order_id`, `order_date`, `order_created_ts`), `shipments`, shipment identifiers/status, `total_bags`, `total_details.pieces`, `total_details.total_price`, and `prices` such as `delivery_charge`, `coupon_value`, `value_of_good`, `price_marked`, `discount`, `gst_tax_percentage`, `cod_charges`, and `amount_paid`.

The docs expose item/bag identifiers and quantities in nested schemas, including `line_number`, `identifier`, `quantity`, `size`, `brand`, `variants`, `order_item_id`, and article/channel identifiers. A synthetic shape for adapter tests (not copied from a customer response) is:

```json
{"items":[{"order_id":"ORDER-SYNTHETIC","shipments":[{"shipment_id":"SHIP-SYNTHETIC","shipment_status":{"current_shipment_status":"delivered"},"bags":[{"line_number":1,"identifier":"SKU-SYNTHETIC","quantity":2,"size":"500 g","brand":{"name":"Example"},"variants":{}}]}]}],"page":{"current":1,"size":1,"has_next":false}}
```

`delivered` should be treated as a documented status value/example of current shipment state, not as proof that every application uses the same lane or status code. The list endpoint also documents `status`/`statuses` filters, but the mapping of codes to configured lanes is application-specific.

## Verified Storefront cart schemas

The official cart page documents `GET /service/application/cart/v1.0/detail` (`getCart`). Query parameters include `id`, `i` (include all items), `b` (include price breakup), `c` (include COD charges), `assign_card_id`, `area_code`, `buy_now`, `cart_type` (`universal`), and `order_type` (`HomeDelivery` or `PickAtStore`).

`POST /service/application/cart/v1.0/detail` (`addItems`) accepts query parameters `i`, `b`, `area_code`, `buy_now`, `id`, `cart_type`, and `order_type`, plus `AddCartRequestObject`: `items[]` and optional `new_cart`. Each `items[]` `AddProductCart` may contain `quantity`, `item_size`, `seller_id`, `price_factory_type_id`, `parent_item_identifiers`, `product_group_tags`, `article_id`, `article_assignment`, `store_id`, `display`, `order_type`, `item_id`, `extra_meta`, `_custom_json`, `meta`, `pos`, `seller_identifier`, `journey`, `fulfillment_mode`, and `promo_id`. The documented add response includes `success`, `cart`, `partial`, `message`, `result`, and nullable `error_code`.

`PUT /service/application/cart/v1.0/detail` (`updateCart`) accepts `id`, `i`, `b`, `area_code`, `buy_now`, `cart_type`, and `order_type`. Its `UpdateCartRequestObject` requires `operation`, whose documented enum is `update_item` or `remove_item`; it may include `items[]` (`UpdateProductCart`) and `free_gift_items[]`. Update item fields include quantity, item size/index, identifiers, article/item/store IDs, metadata and journey. The response includes `message`, `result`, `cart`, `success`, and nullable `error_code`.

`POST /service/application/cart/v2.0/checkout` (`checkoutCartV2`) accepts query parameters `buy_now`, `c` (include cart data; default true), and `cart_type` (`universal`), plus a body requiring `payment_methods` and `payment_mode`. Other documented body fields include `cart_id`/`id`, `address_id`, `billing_address_id`, `aggregator`, `merchant_code`, `payment_identifier`, `payment_params`, `order_type` (`pickAtStore` or `HomeDelivery`), `callback_url`, `delivery_address`, `billing_address`, `customer_details`, `custom_meta`, `meta`, `extra_meta`, `ordering_store`, and card fields (`iin`, `network`, `type`, `card_id`).

These are published schemas. One authenticated cart read returned a complete but invalid snapshot. No cart mutation, quote, or checkout has been executed against the user's live account. (Status at the earlier 18 October validation; see the next section for the implemented requests and their live status.)

## Implemented consumer-lane commerce requests — 18 October 2026 (evening)

The adapter follows the published schemas above. Where the docs leave choices open, it follows request shapes **observed in JioMart's public web code**. That is static evidence of what the website sends. It is not live verification for this integration, and the live status column above remains authoritative. All writes require `JIOMART_CART_WRITES`; payment options and checkout also require `JIOMART_CHECKOUT`. Every cart/checkout call first re-verifies the authoritative `/session` account.

## Late evening 18 October: redirects, payment session, refresh and payment modes

Live results in this section were observed on the real account on 18 October; everything else is implemented and tested with fake transports. See [status](project-status.md).

**Extension redirects (`_account_request`).** Cart writes, address selection, payment options, cart meta, the checkout POST and storefront order reads accept one 307/308 redirect. The adapter repeats the same method and body (dropping its own query parameters, because the `Location` carries them). A redirect from `api.jiomartjcp.com` to an `/ext/…` path is rewritten to `www.jiomart.com`, because JioMart extensions answer only on the storefront host. When the host changes, the session cookie is sent as an explicit header. The target must be HTTPS on `api.jiomartjcp.com` or `www.jiomart.com`, without credentials, under `/service/application/`, `/api/service/application/` or `/ext/`; anything else is `unsafe_redirect`, and a second redirect is `redirect_loop`. Catalog search keeps its separate `/ext/vertex/` redirect rule. Observed live: select-address → `/ext/jmshipmentfee/cart/v1.0/select_address`.

**Storefront order fallback.** `list_orders` retries `GET https://www.jiomart.com/api/service/application/order/v1.0/orders` with the session cookie when the API host returns no orders. `get_order_detail` retries `…/orders/{order_id}` there when the API host returns HTTP 404. Fallback failures are swallowed and the original result or error stands. Logs: `orders_source host=storefront`, `order_status_source host=storefront`.

**Payment modes.** `online_payment` picks the first option named `JIOPP` or `JIOPPLINK` that has a vetted `api_link`, taken from `payment_meta` or else from `payment_flows[aggregator]`. `cash_on_delivery` picks `COD` or `JIOPP_COD` whose first entry has code `COD`. Observed live: JIOPP with aggregator JioOnePay and a `www.jiomart.com` payment link, JIOPP_COD and COD. The bot offers online payment only when `JIOMART_ONLINE_PAYMENT` is true and a public origin exists.

**Payment session (`open_payment_session`).** JioMart's website POSTs the checkout's merchant IDs to the payment link from the signed-in browser. A browser opened from WhatsApp has no JioMart sign-in, and live direct attempts failed with "Invalid session" or HTTP 405. The bot therefore makes the call itself when the customer opens `/pay/{token}`:

1. POST the stored fields (form-encoded) to the vetted `api_link` with the account's cookies and application headers.
2. Follow at most six redirects while the target stays on a `jiomart.com` or `jiomartjcp.com` host; 301/302/303 switch to GET. The first redirect that leaves JioMart is returned as `{redirect}`.
3. A final 200 HTML page yields its first form (`action` resolved to HTTPS, method, named inputs) as `{form}`; a 200 JSON reply yields a payment URL as `{redirect}`. HTTP 401/403 is `auth_expired`; anything else is `no_payment_page`.

Observed live: `www.jiomart.com` payment session → 302 → `store1.jiomartjcp.com` HTML form → `payments.jio.com`, then a UPI payment. A payment session opens only once. Logs record only hop number, status, host, content type, form host and field names.

**Session refresh.** JioMart access tokens appear to last about one hour. On HTTP 401/403 for any stage except `begin_login`, `verify_login`, `verify_session`, `token_refresh` and `app_token`, `_refresh_session` finds the JWT-shaped access cookie. It POSTs `{"access_token": <cookie value>}` to `/service/application/user/authentication/v1.0/token/refresh`, the documented `RefreshTokenRequestSchema`. On HTTP 200 it copies any returned `access_token` into that cookie and retries the original request once. A 401/403 means the request was not processed, so the retry is safe for writes and checkout. The earlier body-less refresh returned HTTP 400 live; the corrected body is unverified. Logs: `session_refreshed`, or `session_refresh_failed` with a status, `transport` or `no_access_token` plus cookie names only. (Superseded on 19 October: both 400s came from the refresh URL missing the path-scoped `R.session` cookie; see [the live refresh contract](#19-october-2026-live-capture-token-refresh-contract).)

## Catalog availability contracts

The official catalog page documents `GET /service/application/catalog/v1.0/products/stock-status` (`getProductStockByIds`). It accepts optional query identifiers `item_id`, `alu`, `sku_code`, `ean`, and `upc`; each identifier is limited to 50 values per request. The published success item shape includes `uid`, `item_id`, `identifier` (for example `sku_code`), `size`, `quantity`, `company`, `seller_identifier`, `store`, `price` (`effective`, `marked`, `currency`), and optional `price_marked`, `price_effective`, `price_selling`, `discount_meta`, and `discount_applied`. This is the documented stock quantity response; it has not been called against the live account.

`GET /service/application/catalog/v2.0/products/{slug}/sizes` (`getProductSizesBySlugV2`) requires `slug` and accepts optional `store_id` or comma-separated `store_ids`. The documented response contains `sellable`, `sizes[]` (`display`, `value`, `quantity`, `seller_identifiers`, `is_available`), `size_chart`, and `moq` (`increment_unit`, `minimum`).

`GET /service/application/catalog/v4.0/products/{slug}/sizes/{size}/sellers` (`getProductSellersBySlug`) requires path parameters `slug` and `size`; optional query parameters are `pincode`, `strategy` (`fast-delivery`, `low-price`, or `optimal`), `page_no` (default 1), and `page_size` (default 12). The documented response contains `items[]` with `price_per_piece` and `price` (`effective`, `marked`, `currency_code`, `currency_symbol`), `quantity`, `pincode`, `article_id`, `discount`, `article_assignment` (`level`, `strategy`), `seller` (`uid`, `name`), `store` (`uid`, `name`), `is_gift`, and `is_cod`; pagination includes `current`, `total`, `has_previous`, `has_next`, `item_total`, and `type`, plus `sort_on` entries.

The published `sellable`, `is_available`, and `quantity` fields are useful validation inputs, but missing booleans remain unknown and none of these fields proves that a requested cart quantity remains available through checkout. A live size lookup for one location-scoped Amul-curd search candidate returned one normalized size marked available with a positive quantity and seller identifiers. The corresponding exact documented seller request returned HTTP 400; this single candidate does not establish that every seller lookup fails, so seller selection and its consumer-lane routing remain unresolved. The authenticated cart read returned an invalid snapshot and did not perform a mutation.

`jiomart.py` now implements `cancellation_reasons`, `cancel_shipment`, and `invoice_pdf` for a single shipment. Nothing below has been called against the live account; this section records the contract each method follows and its evidence source so the next engineer can verify it before relying on it. Both the cancellation methods are gated by a new constructor flag (`enable_order_cancel`, wired from `Settings.jiomart_order_cancel` / env `JIOMART_ORDER_CANCEL`, default off) that is independent of `JIOMART_CART_WRITES`/`JIOMART_CHECKOUT`; `invoice_pdf` is an authenticated read and carries no separate flag, matching `get_order_detail`/`track_shipment`.

**What was implemented — the documented Storefront contract.** This is what the adapter actually calls, on the same `api.jiomartjcp.com` host and with the same conventions (`_request`/`_account_request`, bounded upstream hints, no bodies/tokens/phones logged) as every other order/cart call in this file:

| Step | Request as implemented | Basis |
|---|---|---|
| Cancellation reasons | `GET /service/application/order/v1.0/orders/shipments/{shipment_id}/reasons` (`getShipmentReasons`). Response `{"reasons": [{"reason_id", "reason_text", "priority", "show_text_area", "feedback_type", "flow"}]}` is reduced to `[{"id": reason_id, "text": reason_text}]`, bounded to 20 entries, 160-character text | Published Storefront Order docs |
| Cancel a shipment | `PUT /service/application/order-manage/v1.0/orders/shipments/{shipment_id}/status` (`updateShipmentStatus`), body `{"statuses": [{"shipments": [{"identifier": shipment_id, "status": "cancelled_customer", "reasons": {"entities": [{"data": {"reason_id", "reason_text"}}]}}]}]}`. This is a **full-shipment** cancellation only; the documented per-bag path (`reasons.products[].filters[]` with `line_number`/`identifier`/`quantity`, and the sibling `getShipmentBagReasons` reasons lookup) is not implemented | Published Storefront Order/Order-Manage docs (`UpdateShipmentStatusPayload`) |
| Invoice lookup | `GET /service/application/order/v1.0/orders/shipments/{shipment_id}/invoice` (`getInvoiceByShipmentId`), response `{"success", "shipment_id", "presigned_url", "url", "entity_id", "expires_in", "presigned_type"}`. A 404 is treated as "not generated yet" (`invoice_unavailable`), not a hard failure | Published Storefront Order docs |
| Invoice download | The `presigned_url` (else `url`) from the lookup above is fetched directly (not through `_account_request`), with no redirects followed. Current rule (19 October): HTTPS only, and the host must be exactly, or a dot-separated subdomain of, `jiomart.com`, `jiomartjcp.com`, `fynd.com`, `pixelbin.io` or `jiocommerce.io` (`_INVOICE_HOSTS`; otherwise `invoice_host_blocked`). Earlier draft: a plain suffix match on `jiomart.com`/`jiomartjcp.com`, which would also have accepted a host such as `evil-jiomart.com`. Capped at 5 MB by `content-length` and by streamed size; the body must carry a `pdf` content-type or start with the `%PDF` magic bytes | Adapter-local safety policy; the presigned host itself is unverified (the Fynd platform domains are an assumption) |

Response classification for `cancel_shipment` follows the existing `checkout()` precedent: an explicit failure envelope (`success: false`, `error`, …) on a 2xx response is a definite `rejected`; a transport error or HTTP 5xx is reported as `unknown` (a new `CommerceError` code for this pair of methods) so the caller never retries blindly; HTTP 400 is folded into `rejected` via the existing `error_code=` mechanism; 401/403/429 keep their existing `auth_expired`/`rate_limited` codes from `_request`.

**What the live storefront actually does instead (from the ~11 MB minified `themeBundle` UMD bundle, not called by the adapter).** Searching the bundle for `getShipmentReasons`, `updateShipmentStatus`, `cancelled_customer`, and the order-detail page's cancel button showed that jiomart.com's My Orders page does **not** call the generic Storefront routes above for a customer-initiated cancellation. It calls one of two JioMart-specific extensions, selected by an `ul_order` flag on the order:

- A legacy path, `POST {origin}/ext/ul-backend/v1/orders/{order_id}/cancel_request` with body `{origin: "Web", consumer_email, consumer_phone_number, reason_for_cancellation: "Others", additional_comments, shipments: [{shipment_id, item_name, total_price, item_code}]}`. `/ext/ul-backend` is the same legacy "UL OMS" extension this document already records as authenticating with jiomart.com **website** cookies this bot does not hold (see "Legacy order history" above) — so this path is assumed unreachable for the bot's session and was not implemented.
- A newer `/ext/hellcat/...` extension: `GET {origin}/ext/hellcat/shipment/reason?shipmentId=…[&bagId=…]` for reasons, and `POST {origin}/ext/hellcat/order/fullcancel` / `.../order/partialcancel` to cancel. These functions exist in the bundle (module exporting `getHcatReasons`, `fullCancelOrder`, `partialCancelOrder`, `itemcancelVerify`) but no call site with a literal request body was found in this single bundle file — the page that invokes them is apparently in a separate, not-provided chunk — so their exact JSON shape could not be recovered. `/ext/hellcat` also requires a separate token exchange (`GET /ext/hellcat/sso/generate-token`, `credentials: "include"`) that none of the adapter's other `/ext/...` calls need, which is further evidence this extension may not accept the bot's existing JCP session cookie as-is.
- Invoice download on the live site also bypasses the documented route: the "View Invoice" button calls `GET {origin}/ext/ul-backend/v1/invoice/download/{order_id}` (note: keyed by **order_id**, not shipment_id), gated on a truthy `invoice_url`/`show_download_invoice`-style flag. This is the same legacy UL-backend host as above, so it is assumed to need website cookies the bot lacks and was not implemented either.

Given this, confidence is: **documented-contract routes above — schema is complete and internally consistent with the existing adapter's host/auth pattern, but it is unverified whether JioMart's gateway accepts a customer cancellation or invoice fetch on these generic routes rather than requiring the `/ext/hellcat` or `/ext/ul-backend` extensions.** This must be checked live, behind the `JIOMART_ORDER_CANCEL` flag, before it is trusted. If it turns out the generic routes 404/403, the next step is tracing the hellcat extension's actual call sites (they are not in this bundle) rather than guessing its body shape.

**Shipment/item summary additions (additive only; existing keys and behavior unchanged).** `_shipment_summary` now also returns `can_cancel` and `invoice_available`, both `bool | None` (`None` when JioMart didn't send a strict boolean, instead of silently defaulting to `False`). `invoice_available` prefers the documented `show_download_invoice` boolean and falls back to a truthy `invoice.invoice_url` (nested, per docs) or a flat `invoice_url` (seen on the website's per-shipment view). `_order_item` now also returns `bag_id` (from `prices.id`, documented as "the unique identifier for the order item", falling back to a flat `bag_id`), `line_number` (documented bag-level field), and `identifier` (a flat `bag.identifier` if present, else the documented SKU field `item.code`, else `identifiers.sku_code`) — these are the fields a partial/bag-level cancellation or a cancellation-eligibility display would need; `cancel_shipment` itself only uses the shipment identifier since it only performs full-shipment cancellation. The exact nesting of `identifiers`/`code` could not be confirmed beyond the flattened docs page's field order, so `identifier` tries the most specific, most documented source first. One exact-dict-equality assertion in `tests/test_orders.py` (owned by the order-flow rewrite in progress elsewhere) failed at the time because of the added keys. (Resolved by 19 October: the full suite, 307 tests, passes.)

## 19 October 2026: proactive refresh, keep-alive, cancellation and invoices wired into chat

Implemented and tested with fake transports (307 tests); **nothing in this section has been called against the live account yet.** See [status](project-status.md).

**Why the sign-in still expired hourly.** Live logs on 18–19 October showed `session_refresh_failed status=400` followed by HTTP 401 about every hour. The bot refreshed only after a 401, when the access token had already expired. JioMart's storefront bundle refreshes proactively, at most about 120 seconds before the token's `exp`, and sends the refresh with the session cookie alone.

**Proactive refresh (`_request`).** Before any request outside the login stages, the adapter reads the unverified `exp` claim of the JWT-shaped access cookie. If 300 seconds or less remain, it refreshes first. It makes at most one refresh attempt per request, so a proactive refresh is not followed by a second after-401 refresh; the after-401 path still covers tokens without a readable `exp`. Account requests (`_account_request`) go through the same path.

**Refresh variants (`_refresh_session`).** First the documented `RefreshTokenRequestSchema` body `{"access_token": <cookie value>}`; if JioMart answers HTTP 400, once more with no body (cookie only), as the website does. HTTP 200 copies any returned `access_token` into the cookie. Logs: `session_refreshed variant=body|cookie`; `session_refresh_failed status=<n> variant=<v>`, `reason=transport variant=<v>` or `reason=no_access_token cookies=<names>`. Token values are never logged. (Superseded later on 19 October: both variants returned HTTP 400 live because the URL missed the `R.session` cookie path; the adapter now makes one body-less call to the `/api`-prefixed URL. See [the live refresh contract](#19-october-2026-live-capture-token-refresh-contract).)

**Keep-alive (`keep_alive(session, within=900)`).** Used by the background loop in `smartbazaar/session_keepalive.py`. It returns `True` without a request when more than 15 minutes remain; otherwise it refreshes, writes renewed cookies back to the stored session and returns whether the session is still usable. The loop runs every `SESSION_KEEPALIVE_INTERVAL_SECONDS` (default 600) for sessions with a customer message within `SESSION_TTL_SECONDS` (default 30 days). Whether JioMart keeps renewing a session for 30 days is unknown.

**Cancellation in chat.** CANCEL ORDER n (or the order card's Cancel order button) is offered only when `JIOMART_ORDER_CANCEL` is on and the order detail marks a shipment `can_cancel: true`. The confirmation button re-reads the order and, per cancellable shipment, calls the reasons route and then the status route above with a neutral reason. `rejected` means nothing changed; `unknown` (transport or 5xx) is never retried, and the customer is asked to check My Orders. Logs: `order_cancel_failed code=<diagnostic>`. The storefront evidence below (UL OMS and hellcat extensions) still suggests this generic route may not be what jiomart.com uses.

**Invoices in chat.** INVOICE n and the order card's Invoice button call `invoice_pdf` for each of the order's first three shipments that is not explicitly marked `invoice_available: false`; the watcher's Delivered push attaches the first such shipment's invoice. HTTP 404 or a missing URL is "not ready yet" (`invoice_unavailable`, logged at info as `invoice_unavailable code=…`). The download rules are in the corrected table row above.

**Known gap in the payment-session hop check.** `open_payment_session` decides whether a redirect is still on JioMart with a plain suffix test (`hostname.endswith(("jiomart.com", "jiomartjcp.com"))`), not the dot-boundary test now used for invoices and for `_payment_link`. A redirect to a host such as `evil-jiomart.com` would therefore have been followed with the account cookie header (never observed). Fixed later on 19 October: hops now use the same dot-boundary match (`host == h or host.endswith("." + h)`), and `tests/test_commerce_tools.py` checks that a lookalike host is never requested.

## 19 October 2026 (live capture): token refresh contract

Observed about 10:00 IST. The owner signed in to www.jiomart.com in a browser (the website signs in through Reliance's `account.relianceretail.com`, not the bot's OTP routes). The site's own refresh was recorded, variants were sent from the same signed-in page, and one refresh was sent with the bot's stored **local** session (from its OTP login on 18 October; its access token had expired about 17 hours earlier). Only methods, URLs, header and cookie names, body and response keys, statuses and JioMart's error messages were recorded, never a token, cookie value, OTP or phone number.

**What the website sends.** Its SDK (`fpi.auth.refreshToken()`, SDK domain `https://www.jiomart.com/api`, `jwtAuthEnabled` with `jwtTokenRefreshThreshold` 120 s) refreshed right after sign-in, and the same call was triggered once more:

- `POST https://www.jiomart.com/api/service/application/user/authentication/v1.0/token/refresh` with **no body** (no content type) and the browser's cookies (`withCredentials`).
- Request header names: `accept` (`application/json, text/plain, */*`), `authorization` (`Bearer` + base64 of application ID and public application token, the same scheme the bot uses), `visitor-id`, `x-currency-code` (`INR`), `x-fp-date`, `x-fp-sdk-version` (`1.10.3-89`), `x-fp-signature`, `x-geolocation`, `x-location-detail`. There was no `x-application-id` and no `x-user-data`. The page's application ID is the bot's default, `685945f46c8c7aee3f3af605`.
- Response: HTTP 200 with body keys `access_token` (a JWT whose `exp` is 3600 s ahead) and `exp` (the same epoch seconds). Response header names include `x-auth-token`; page scripts cannot see `Set-Cookie` or the httpOnly cookie names.

**What the endpoint requires** (variants sent from the signed-in page to the same URL):

| Variant | Result |
|---|---|
| Cookies plus `authorization` and `accept` only; no body; no `x-fp-*` signing, `visitor-id` or location headers | 200 `{access_token, exp}` |
| No cookies, no body | 400 `Either access_token or refresh token cookie is required` |
| No cookies, documented body `{"access_token": <current access JWT>}` | 400 `No refresh token found in access token` |
| Cookies, no `authorization` header | 401 `Invalid authorization token` |
| `api.jiomartjcp.com` from the page | Blocked by the browser (CORS); no server answer |

The access JWT's claim names are `user_id`, `external_id`, `emails`, `phone_numbers`, `first_name`, `last_name`, `hashed_rr_id`, `rr_id`, `created_at`, `iat` and `exp`. Nothing in it is a refresh token, so the documented body alone cannot work. The refresh token must arrive as a cookie, and request signing is not required.

**Why the bot's refresh returned 400.** The bot's stored OTP session holds three cookies:

- `f.session`: the access JWT, `Domain=.jiomartjcp.com`, `Path=/`
- `R.session`: an opaque refresh token, `Domain=.jiomartjcp.com`, `Path=/api/service/application/user/authentication`
- `AKA_A2`: an Akamai cookie, `.jiomart.com`

The bot posted to `https://api.jiomartjcp.com/service/application/user/authentication/v1.0/token/refresh`. That path is outside `R.session`'s cookie path, so the refresh cookie was never sent, and JioMart answered HTTP 400 to both the documented body and the cookie-only call.

**Proven request (live, the bot's own session).** `POST https://api.jiomartjcp.com/api/service/application/user/authentication/v1.0/token/refresh`. It used the adapter's usual headers (`accept`, `authorization`, `x-application-id`, plus httpx's `content-length: 0`), no body, and the cookie jar, which now sends `R.session` and `f.session`. The result was HTTP 200 with body keys `access_token` and `exp` (3600 s), and `Set-Cookie: f.session` with `Max-Age=3600; Domain=.jiomartjcp.com; Path=/; HttpOnly; Secure; SameSite=Strict`. `R.session` was not re-issued. Without application authorization, all three URLs (API host with and without `/api`, and the storefront gateway) answer 401 `Invalid authorization token`, so all three reach the auth service. A POST without `Content-Length` gets an Akamai HTTP 411. The refresh succeeded about 17 hours after the access token expired, so `R.session` outlives the access token by at least that long. Its actual lifetime, and whether it ever rotates, are unknown.

**Adapter now (`_refresh_session`, `_request`, `keep_alive`).**

- **Request.** One refresh request per call: the URL above, no body, and the cookie jar. The browser-only headers are not sent. On HTTP 200, the returned `access_token` is copied into `f.session` when no `Set-Cookie` already did. A request retried after a refresh rebuilds any explicit `cookie` header from the renewed jar. The adapter sends an explicit header for cross-host storefront requests, which previously would have retried with the old token.
- **Backoff after a failure.** The same access token is not refreshed again for 15 minutes after a 4xx rejection, or for 60 seconds after a transport error, 429 or 5xx. The backoff is kept in memory, keyed by a SHA-256 of the token, and a new LOGIN produces a new token, so it starts clean. While a token is backing off, the proactive refresh is skipped, and a request that gets 401/403 fails as `auth_expired` without another refresh call.
- **Keep-alive result.** `keep_alive` now reports a session as usable when the refresh failed or is backing off but the token has not yet expired.
- **Logs.** `session_refreshed`; `session_refresh_failed status=<n> cookies=<names>`, `reason=transport` or `reason=no_access_token cookies=<names>`; `session_refresh_skipped reason=backoff`. No token or cookie values are logged.

**Still open.** The change has not been deployed to Render. It is proven by one live call with the bot's local session and by tests, but not through a WhatsApp conversation. A session stored on Render may recover without a new LOGIN, because a refresh works on an expired access token, but only if that stored session survives the deploy (the free service's SQLite is ephemeral) and its `R.session` is still valid.
