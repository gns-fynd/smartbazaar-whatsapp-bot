# Login and search POC module

## Purpose and boundary

The `smartbazaar/` package is currently one deliberately small application module. It owns request ingress, local persistence, login/search conversation flow, catalog matching, Meta delivery, and external adapters. Keeping this together is appropriate for the local POC because account linking, multimodal shopping, local drafts and memory share one controlled request lifecycle, and no durable cross-service contract exists yet.

It is not an order system. `conversation.py` mutates only a local draft; `jiomart.py` exposes history/cart reads and disabled-by-default cart add/update adapters, but no checkout/payment/order submission; and its public endpoints are limited to health, privacy, and webhook verification/receipt. Future cart and checkout code should become distinct module boundaries after its upstream contract, confirmation versioning, and reconciliation rules are known.

*Update, 18 October 2026 (evening):* the paragraph above describes the earlier build. The package now also contains flag-gated commerce flows: `checkout.py` (real cart sync/edit, review, confirmed checkout, payment links), `orders.py` (order history, tracking, reorder) and `order_watch.py` (order-status pushes). They stay inside this module rather than a separate service because they share the owner lock, encrypted store, conversation routing and outbox. Their boundary is a set of classes called by `conversation.py` and `app.py`, and `jiomart.py` remains their only path to JioMart. The public surface adds `/pay/{token}` and `/paid/{token}`. Live cart writes and order placement are not yet verified.

*Update, 19 October 2026:* the local shopping list is retired; `tools.py` writes confident matches straight into the real cart through `checkout.py`, and ambiguous products are short-lived questions. Two modules were added inside this boundary: `session_keepalive.py` (background JioMart session renewal, started by `app.py`) and `receipt.py` (in-memory order-summary PDF used by `checkout.py` and `order_watch.py`). `orders.py` gained flag-gated cancellation and invoices. None of this is deployed or live-verified yet. See the section at the end.

## Runtime flow

1. `create_app` builds dependencies from `Settings` and starts two inbox workers, one outbox worker and (since 19 October) the session keep-alive loop. When checkout is enabled, it also resolves the public origin and starts the order-watch worker. It also closes the commerce, Meta, model and SQLite clients on shutdown.
2. The POST webhook caps the body at 256 KiB and verifies the raw bytes with Meta's HMAC. It accepts only the configured WABA, phone-number ID and sender allowlist. It digests the WABA/sender identity for local ownership and claims the provider event before queueing it.
3. An inbox worker obtains an owner-specific `asyncio.Lock`, invokes the conversation, encrypts the resulting reply into the outbox, and completes the event. Its `asyncio.Queue` is intentionally in memory, so a process death cannot reconstruct raw inbound content.
4. `Conversation` handles logout/cancel/login/OTP/pincode/address locally. Non-sensitive greetings, help and grocery conversation reach the planner before or after login. Only connected sessions can execute shopping tools. Planner context includes bounded product/list/preference fields, recent queries, a validated pincode, a connection flag, and at most eight sanitized recent user/assistant messages.
5. The JioMart adapter performs the bounded search. It records `coverage: partial` when paging evidence is incomplete. The model ranks a capped candidate set; catalog code discards invented IDs and rejects candidates that fail hard identity or relevance conditions.
6. The outbox worker obtains the next encrypted payload, calls the Meta transport, and records accepted/failed delivery state. HTTP 401 also sets process-local transport health to `auth_rejected`; provider acceptance resets it to `available`. Health starts `not_observed` and makes no network probes. Delivery retries have no commerce side effect: they resend an already-generated message and never rerun a cart write or checkout, even though the flag-gated checkout flow can now mutate commerce state.

Credential checks now run before serving and every configured interval (five minutes by default). Cached results expose earliest positive expiry and degrade readiness within 24 hours. `/readyz` returns HTTP 503 on credential, worker or observed delivery degradation. Reads cannot prove end-to-end delivery. Outbound 401/403 preserves a recent reply in encrypted `auth_wait` with one-minute retries for at most 15 minutes; expired waiting replies fail without later replay. Ordinary transient errors retain the existing attempt cap. See [operations](../../docs/operations-reliability.md) for current runtime and supervision acceptance.

## State and security constraints

`Store` sets restrictive permissions on the database parent/path, encrypts session and outbound payloads, and uses HMAC digests for indexed event/provider IDs. It stores a sanitized, bounded recent conversation window, never raw webhook bodies or OTPs. The underlying Fernet key must remain private and stable for as long as encrypted records are needed. Session expiry (30 days after the customer's last message since 19 October; 24 hours before) and cleanup are local POC behavior, not a proven JioMart session-lifecycle contract.

Inbound security is layered: Meta signature first, expected account identifiers second, sender allowlist third, freshness and deduplication last. This scope is suitable for a controlled test sender, not general public enrollment. The source code must not log exception payloads because an upstream failure can contain tokens or customer content.

OTP has a separate path before the model. Conversation code rejects unsolicited codes, passwords/API-key-like content, and phone-like values outside a link flow. The app needs a private Meta app secret before signed webhook verification can work in a real deployment; a fresh test access token alone is insufficient.

## External dependencies

`httpx` is used by both external clients. `JioMartClient` validates catalog redirects to the expected `www.jiomart.com/ext/vertex/` path, which was discovered by the adapter/test contract; it must not follow arbitrary redirects. Account requests accept exactly one 307/308 to `api.jiomartjcp.com`/`www.jiomart.com` under `/service/application/`, `/api/service/application/` or `/ext/`, with `/ext/` moved to `www.jiomart.com`. The payment session follows up to six hops only on JioMart hosts. Pillow (`pillow>=11`) is a runtime dependency for the cart picture. `AsyncOpenAI.responses.parse` is used with Pydantic structures, bounded input/output, low reasoning effort, a 25-second timeout, one retry and `store=False`. Live checks exercised intent/ranking, bounded JioMart search, one available product-size response, and an authenticated cart read whose complete snapshot remained invalid. They do not establish quantity stock through checkout, seller routing, cart mutation, or order behavior.

Authentication responses use endpoint-specific validation: OTP login requires an existing-user indicator and user object, and the following session call requires its user object and matching account/application. A shared `success` flag is not required because the documented response schemas differ. Explicit error envelopes remain failures. A new login carries the verification-issued cookie directly into `GET /session`; it does not invoke token refresh, which is documented as a separate expired-token operation with body and trusted-user-context requirements. (Late evening, 18 October: after login, a 401/403 on any non-login stage calls refresh with `{"access_token": <JWT cookie>}` and retries once; this is unverified live.) Failures emit only bounded internal stage, HTTP status, and diagnostic-code fields; provider bodies and authentication material remain excluded. Regression coverage includes the exact verify/session sequence, cookie continuity, flagless success, HTTP 400 invalid OTP, explicit failure envelopes, authoritative identity mismatch, and redacted diagnostics. The corrected runtime authenticated the real account, loaded its saved default address and completed an inbound search.

## Interactive product replies

Search can produce a structured product card using `catalog.py` image normalization, `Conversation._product_card`, the encrypted outbox and `WhatsApp._payload`. Cards use the real allowlisted catalog image, one leading validated product per query, listing price and browse-only reply buttons. Plain text remains the fallback for missing images and transports without interactive support. `app.py` routes Meta `interactive.button_reply` IDs into the deterministic conversation handler before the language model.

Button actions live in encrypted per-owner session state with random opaque IDs and a 15-minute expiry, binding to the account and delivery context. They return details or the next existing candidate, never add to cart or purchase. Unknown/stale/other-owner IDs fail closed. The finite candidate set and compact card prevent an entire broad search page from flooding the chat. See [reply formats](../../docs/whatsapp-reply-formats.md).

## Expanded agent tools and memory

`ShoppingAgent.interpret` returns typed `Intent`/`ShoppingLine` actions including add/replace/review/remove/set_quantity/choose/history/remember/memory/forget/new_session. The model cannot choose account IDs, URLs or arbitrary API payloads. `ShoppingTools.execute` is the deterministic dispatcher. It searches and ranks bounded candidates, applies the existing catalog veto, then records exact selections or unresolved lines in a maximum 30-line local draft. One current choice is surfaced at a time; resolving it activates the next unresolved line's retained options. Choices are version/pincode/expiry-bound.

`memory.py` owns alias normalization, preference precedence, session rotation and list rendering. `Store.get_memory/save_memory/forget_memory` owns encrypted persistence independently of login TTL. Explicit preferences require a selected matching product and an explicit remember request; up to 50 expire after 180 days. Delivered purchase evidence includes source order/date and must be recent before personalization. Retrieval failure supplies no negative preference. LOGOUT removes owner memory; FORGET clears the current account's memory and suppresses automatic history reimport.

`media.py` downloads only signed Meta attachment references from allowlisted HTTPS hosts and caps audio/image bytes. Whisper converts supported audio to bounded text; Responses vision extracts product queries. The worker requires a connected account and no OTP challenge before download. `Conversation.handle(..., shopping_only=True)` permits only search/add decisions from media. No media bytes, OTPs or growing dialogue transcript are persisted.

New tests live in `test_shopping_tools.py`, `test_media.py` and `test_commerce_tools.py`, with webhook media coverage in `test_app.py`. Provider mocks establish local behavior, not real media quality, quantity availability or purchase success. See [architecture and remaining gates](../../docs/agent-architecture.md).

## Conversational entry and presentation

`Conversation.handle` resolves owner-bound quick actions, runs the OTP-first control path, then records an eligible sanitized exchange. The guest path invokes the same typed planner but never dispatches a model-selected commerce action. Connected greetings/help are no longer fixed pre-planner responses. `Intent.reply` supplies conversational prose; `presentation` and `quick_actions` choose only allowed output layouts and navigation. Tool receipts remain authoritative and cannot be replaced by invented planner prose.

The encrypted `sessions.data.dialogue` window contains at most eight user/assistant messages, each 480 characters. Day/idle/account rotation excludes stale exchanges from model context. Login/OTP/addresses and common secret/contact patterns are excluded or redacted. New login, logout, forgetting and fresh-session actions clear dialogue. Guests remain isolated by channel owner. Tests in `test_chat_experience.py` cover these boundaries; `test_app.py` covers signed guest ingress to interactive outbox delivery.

## Real cart, checkout, payment and order updates — 18 October 2026

Implemented and locally tested behind `JIOMART_CART_WRITES` and `JIOMART_CHECKOUT` (both default off; on in the runtime since 21:47 IST, 18 October). Live verification so far covers only a real CART read and the pay route being reachable. See [project status](../../docs/project-status.md).

### Key components

- `CheckoutFlow.view_cart` / `edit_cart` render the real cart with JioMart's fee breakup and remove or re-quantify lines. Lines are chosen by number (from a 30-minute, account/address-bound `cart_view`), by name (asking when ambiguous) or as all unavailable lines. Re-quantifying needs exactly one target line; quantity 0 removes.
- `CheckoutFlow.prepare` handles CHECKOUT. It returns the attempt status if a submitting/unknown attempt exists. *Earlier:* it re-found up to 10 list products lacking cart IDs by exact catalog ID, built wanted lines (summing duplicates), added missing lines and updated changed quantities. *Now:* it adds nothing unless `add_list=True` (ADD MY LIST), which calls `sync_list`. It then selects the saved address (recording `address_selected`) and calls `_review`.
- `CheckoutFlow.sync_list(state, memory, only=None)` refreshes stale cart references (up to 10, exact catalog ID only). `_wanted_lines` keeps one line per (item, size) at the **larger** quantity, clamped to JioMart limits. It adds only products not already in the cart (batches of 20), never re-quantifies existing ones, and removes moved lines from the list. `only` (a set of line `id()`s) limits the move to the current request's new or resolved lines; `Conversation._move_to_cart` passes it after add/replace/choose.
- `_review` re-reads the cart and renders every line (marking `just_added` ones), the notes, the pending-choice count (only with ADD MY LIST), the charge breakup and blockers. If there are none it asks for payment options and creates `place_order` `sbco_` buttons per method in `state["checkout"]`. It returns a picture `cart_card` (side notes as a separate text) or, without images, text plus a quick reply. *Earlier* it separated list lines from other lines and offered `remove_others`.
- `view_cart` returns a `cart_card` with navigation buttons `go_checkout` (Checkout) and `empty_cart` (Empty cart) when cart writes are on; `empty_cart` removes every line in one `remove_item` request.
- `_breakup_lines` shows Items, Discount, Coupon, Delivery, Cash on delivery fee and Convenience fee. When at least ₹0.50 is unexplained it adds “Delivery & other charges” for the remainder, then Total.
- `handle_button` pops the action and rejects it if expired or bound to another account/address. `go_checkout`/`empty_cart` then run directly. For `place_order` it also rejects an older list version, re-reads the cart and compares `_snapshot`, then calls `_place`. A legacy `remove_others` action only replies that the button is no longer used.
- `_place` refuses while an attempt is pending and requires a public origin for online orders. It writes `begin_attempt` (`submitting`) and awaits `asyncio.shield(_submit(...))`. `_submit` calls `JioMartClient.checkout` and classifies the outcome (see gotchas). With an order ID it calls `Store.supersede_unpaid` for older `awaiting_payment` attempts, stores the pay link (`{api_link, fields}` plus order ID and total) for online orders, or clears ordered lines and marks `placed` for cash on delivery, then compares totals.
- `status` / `has_pending` / `needs_status` / `clear_pending` / `_reconcile` implement ORDER STATUS for pending and awaiting-payment attempts (re-sending a live pay link) and CLEAR ORDER CHECK. Reconciliation matches exactly one listed order with the same total created after the attempt start minus two minutes.
- `OrdersFlow.recent` / `detail` / `track` / `reorder` / `button` serve the orders commands; `orders_view` (30 minutes) and `order_actions` (15 minutes, at most nine) are account-bound.
- `OrderWatcher.check` iterates `Store.watched_attempts` under owner locks and calls `_step`. `_step` reads `get_order_detail`, saves refreshed cookies with `touch=False`, maps the stage and decides nudge/give-up/push. It revokes links when leaving `awaiting_payment` and either returns an outbox event or stores `missed_notice`.

### Dependencies

`checkout.py` imports `catalog.normalize_products`, `jiomart.CommerceError` and `memory.bump_draft`. `orders.py` imports `catalog`, `jiomart` and `memory` (`MAX_LINES`, `bump_draft`, `canonical_query`). `order_watch.py` imports `checkout.clear_ordered_lines` and `jiomart.CommerceError`. `conversation.py` constructs `OrdersFlow` and accepts an injected `CheckoutFlow`. `app.py` constructs both `CheckoutFlow` (with a `public_origin` callable) and `OrderWatcher`. ### Gotchas

- Two gates: `JioMartClient` refuses writes/checkout without its constructor flags, and `CheckoutFlow` checks its own copies. The agent's capability flags only shape instructions. With cart writes off, CART is rerouted to the local list review.
- Outcome classification in `_submit`: `auth_expired`, `rejected` and `changed` codes, and other 400/404/409/422 responses, mean `failed` (nothing placed). `JioMartClient.checkout` turns any pre-POST failure into `rejected`/`changed`. Transport errors, 5xx, a missing order ID, `success:false` with an order ID (`unknown` code) and cancellation (`BaseException`) mean `unknown`, which blocks new orders.
- `begin_attempt` keys the row by an HMAC of the button ID with `INSERT OR IGNORE`. A second use returns “already used”, and the button is also popped from session state.
- `/pay` serves only while the attempt is `awaiting_payment`. `/paid` never changes state itself; it only schedules `check_orders(only=attempt_id)`.
- Fixed late evening: ORDER STATUS calls `CheckoutFlow.status` for `submitting`/`unknown`/`awaiting_payment` (`needs_status`) and re-sends a live pay link with a note that an already-opened JioMart payment page needs a fresh CHECKOUT (sessions open once).
- HISTORY maps to the orders list; asking for it clears FORGET's `history_import_disabled` so purchase evidence can be imported again.
- Fixed (late evening): the buy/order search prefix follows `checkout_enabled`; the `jiomart.py`/`tools.py` docstrings, `_cart_text`, `OrdersFlow.reorder` and the planner's checkout instruction now say products go straight to the cart and CHECKOUT only reviews it. REORDER moves found items into the cart like an add; typed “add to cart” means ADD MY LIST.
- `Store.save(owner, state, touch=False)` must be used by any background reader of a session (watcher, `/pay`, and since 19 October the keep-alive); ordinary saves extend the session TTL (24 hours then, 30 days since 19 October).
- WhatsApp's window is checked against `state["last_inbound"]` with a 23.5-hour margin. Only the latest attempt's `missed_notice` is shown on the next message.

### Key components

- `Composer.apply(customer_text, replies)` joins string replies into a draft and takes the `body` of the first `quick_reply`/`cta_url`/`cart_card` as the prompt draft. It calls `agent.compose_reply` and keeps the model's message or prompt only when `faithful` passes and the length limits hold. It logs `compose message=… prompt=…`. `Conversation._composable` excludes empty and `Written` replies and non-memorable inputs (login/OTP/address/pincode/forget/logout/cancel, digits, phone-like, secrets, `sbqa_`/`sbch_` taps). It includes `sbco_`/`sbor_`/`sbpc_` taps.
- `ShoppingTools.next_choice` emits a `list` message with `sbch_` row tokens saved in `memory["choices"]["tokens"]`. `Conversation._choice_command` maps a tapped token to “choose N” (“choose 0” when unknown).
- `JioMartClient.open_payment_session(session, api_link, fields)` returns `{redirect}` or `{form}`. `/pay` calls it under the owner lock and saves the session with `touch=False`.
- `OrderWatcher._step`: a `CommerceError` on an `awaiting_payment` order older than 3 hours sets `unpaid` and deletes links without a message.

### Dependencies

`conversation.py` imports `composer.Composer`; `composer.py` imports `memory.safe_turn`; `whatsapp.py` imports `cart_image` (which imports Pillow and `httpx`). There are no import cycles.

### Gotchas

- With cart writes on, `_move_to_cart` strips “Saved as a shopping list…”/“On your shopping list…” lines from the tool replies and appends “🛒 Added to your JioMart cart: …”. A sync failure appends the failure text instead.
- `CheckoutFlow` and `JIOMART_ONLINE_PAYMENT` both default online payment off; tests pass `online_payment=True` explicitly.
- The cart card's `items` hold only image URLs and quantities. Its text fallback must stay complete, because the outbox swaps it in on any non-auth send failure.
- Deploys must wait for no `processing` event and no `pending` or `sending` outbox row; restart turns `sending` back into `pending` and can duplicate a message.

## 19 October 2026 — single basket, buttons, keep-alive, cancel, invoices and summaries

Implemented and locally tested (307 tests; Ruff passes). Not deployed and not verified on WhatsApp or against JioMart. See [status](../../docs/project-status.md) and [ADR 6](../../docs/architecture/decisions/0006-jiomart-cart-is-the-only-basket.md). This section supersedes the earlier sections of this file where they differ.

### Key components

- `ShoppingTools._add` searches and ranks each item, takes a matching saved preference or a single exact match as confident, and calls `_receipt` → `CheckoutFlow.add_products` once for all confident lines. Everything else becomes `memory["pending"] = {items, pincode, expires}` (at most three options per item, `PENDING_TTL` 6 hours); the previous `pending` is always dropped first. `intent.viewed` adds `focus(state)` (the product just shown, 6 hours, same pincode) instead of searching. `_choose`/`_skip` pop the current question and ask the next via `next_choice`, which issues fresh `sbch_` tokens (index `-1` = Skip) and returns a `choice_card` when all options have images, else a `list` menu.
- `CheckoutFlow.add_products(state, memory, lines)` refreshes up to 10 stale references by exact catalog ID, builds `_wanted_lines` (larger quantity for duplicates, limit clamps with notes), skips products already in the cart, adds the rest in batches of 20, stores product details in `memory["cart_products"]` (≤40) and sets `state["just_added"]`. It returns `{added, already, notes, error}`; a JioMart rejection or unsafe identifiers set `error` and stop.
- `CheckoutFlow._remember_view` now stores line names and quantities (≤30) for 6 hours; `view_context` returns them as planner `cart` context when the binding still matches. `cart_item(state, n)` resolves "remember cart line n".
- Checkout buttons (`_button`) carry kind, snapshot, binding, expiry (`CONFIRM_TTL` 30 minutes) and method; there is no `draft_version`. Navigation kinds are `go_checkout`, `keep_shopping`, `empty_cart` and `remove_unavailable`; only `place_order` compares the snapshot and submits. A blocked review offers Remove unavailable (when relevant) / Keep shopping / Empty cart.
- `Conversation._with_buttons` runs after composition and the voice prefix. If the last reply is a non-document dict it is left alone. Otherwise the last text (skipping trailing documents) becomes a `quick_reply` with `_next_steps` buttons when it is ≤1,024 characters, else a separate "What would you like to do next?" prompt is appended. `_next_steps` uses session/challenge/location state and `_last_action[owner]`. Quick-action and product buttons share `state["button_actions"]` (`BUTTON_TTL` 24 hours, `MAX_BUTTON_ACTIONS` 40, single-use). A Resend OTP tap re-sends to the challenge's mobile number.
- `OrdersFlow.cancel` → confirmation card (`cancel_confirm`/`keep` order buttons); `_confirm_cancel` re-reads the order and cancels each `can_cancel: true` shipment with a neutral reason (`_reason`). `invoice` calls `invoice_document` for up to three shipments; `invoice_document` turns `invoice_pdf` into a `document` message. Order buttons last 24 hours (≤15 kept); `orders_view` lasts 6 hours.
- `receipt.summary_message(order_id, record)` builds the order-summary `document` from an attempt record (`lines` with `line_total`, `breakup`, `method`, `at`); `CheckoutFlow._submit` appends it to the cash-on-delivery reply and `OrderWatcher._step` to the online payment push.
- `session_keepalive.run_keepalive_once` iterates `Store.active_sessions(active_within=…)`, and for each owner takes `locks.setdefault(owner, asyncio.Lock())` (the same map `app.py` uses), calls `commerce.keep_alive(session)` and always saves with `touch=False`.

### Dependencies

`tools.py` imports `agent.AgentError`, `catalog`, `jiomart.CommerceError` and `memory` (`PENDING_TTL`, `PREFERENCE_TTL`, `canonical_query`, `remembered_choice`), and receives `CheckoutFlow` by injection. `checkout.py` imports `catalog.normalize_products`, `jiomart.CommerceError` and `receipt.summary_message` (no longer `memory.bump_draft`). `orders.py` imports `catalog` and `jiomart` (no longer `memory`) and receives `CheckoutFlow` by injection. `order_watch.py` imports `checkout.clear_ordered_lines`, `jiomart.CommerceError`, `orders.OrdersFlow` and `receipt.summary_message`. `conversation.py` imports `catalog.product_link` and constructs `ShoppingTools(commerce, agent, checkout)` and `OrdersFlow(store, commerce, checkout)`. `app.py` imports `session_keepalive.keepalive_loop`. `receipt.py` imports only Pillow and the standard library; `session_keepalive.py` only the standard library. There are no import cycles.

### Gotchas

- With `JIOMART_CART_WRITES` off, `add_products` returns an error and nothing can be added; there is no fallback basket.
- `_choose` drops **all** open questions when the choice is invalid (expired, other pincode, out-of-range number, or an `sbch_` token from an older question, which maps to “choose 0”). An old tap therefore also cleared newer questions. Fixed later on 19 October: an out-of-range number or an old `sbch_` token now replies “That choice is from an earlier request.” and re-asks the current question without discarding it; only an expired question or a pincode change drops them (`tests/test_checkout_conversation.py`).
- `skip` always drops the current (first) question, whichever item the customer named; “I don't want bread” only does what it says when bread is the question being asked.
- `roll_session` drops `draft`/`choices` on the first message after deploy, so lists saved by older builds disappear without being copied into the cart (`tests/test_checkout_conversation.py` covers this).
- `cart_view` lines feed the planner only after the cart was shown (CART, review or an edit); an add alone does not refresh them.
- The keep-alive loop runs even with commerce flags off, and keeps trying sessions whose refresh failed every interval until they expire; `session_keepalive_expired` repeats for them.
- `keep_alive` and proactive refresh trust the JWT `exp` without verifying the signature; an unreadable `exp` falls back to the after-401 refresh in `_request`, while `keep_alive` refreshes immediately.
- Outbox `document` payloads hold the whole base64 PDF (up to 5 MB) in the encrypted row.
- `JioMartClient.open_payment_session` still checks redirect hops with a plain suffix match (`endswith(("jiomart.com", "jiomartjcp.com"))`), unlike the dot-boundary checks in `_payment_link` and `invoice_pdf`. Fixed later on 19 October: hops now use the same dot-boundary match (`host == h or host.endswith("." + h)`), and `tests/test_commerce_tools.py` checks that a lookalike host is never requested.

### Tests

New: `tests/test_session_keepalive.py` and `tests/test_order_actions.py`. Updated suites cover adds into the cart, open questions and their replacement/expiry, skip, picture choices and documents (`test_cart_card.py`), product links, next-step buttons, voice, proactive/cookie-only refresh and `keep_alive` (`test_jiomart.py`), cancel and invoice flows (`test_orders.py`). 307 tests pass.

## 19 October 2026 — personalised substitutions

Implemented and locally tested (353 tests; Ruff passes). Not pushed, deployed or verified live. See [status](../../docs/project-status.md) and [reply formats](../../docs/whatsapp-reply-formats.md). This supersedes the 19 October section above where they differ: a blocked review offers Find substitutes, and a request with no sellable exact match asks a labelled substitute question.

### Key components

- `catalog.product_is_substitute(query, product, wanted=None, *, ranked=False)` is the deterministic substitute gate. A product passes `product_is_relevant` for the query and for `wanted`'s name, and keeps a requested formulation (`_keeps_formulation`, now shared with `product_matches_exact`). It must not share `wanted`'s ID or cart item ID. When both listings have a category, `same_category` decides. Otherwise the requested noun (`_kind`: last word that isn't a size, number, packaging or filler, such as `bar`, `cup` or `pouch`) must be the product's own noun or a word of its category. `ranked=True` (a model alternative) skips only the noun test.
- `ShoppingTools._add`: on no sellable exact match, `_unavailable(products, safe, preference)` returns `(wanted, note)`. `wanted` is the usual product when it is listed unsellable or wasn't returned, or the first exact ID listed unsellable. `note` is “Your usual X is unavailable.”, “I couldn’t find your usual X near you.” or “X is unavailable.”. With other sellable exact matches (the usual is gone), those become the options. Otherwise `_substitutes` picks them, and a question with no note gets “I couldn’t find “query” near you.”. The pending item carries `substitute: {"note": …}`. `_add` now clears `products` on `AgentError`, so an unranked search offers nothing.
- `ShoppingTools._substitutes(state, memory, query, products, wanted, ranked)` pools sellable search results. When no bought-before product is in the pool, it looks up at most `MAX_USUAL_LOOKUPS` (1) bought-before product that passes the gate by name, and keeps only the same catalog ID, still sellable. It gates, sorts (bought, same category, ranked, search order), keeps `MAX_SUBSTITUTES` (3) and marks usual ones through `_usual_first`. `_bought(memory)` is the shared history map (empty after FORGET).
- `ShoppingTools.cart_substitutes(state, memory)` needs `cart.cart_writes` and a location. It reads `CheckoutFlow.unavailable_lines` and refreshes history. For at most `MAX_SUBSTITUTE_LINES` (3) lines, it searches the line's name, takes the category from JioMart's own listing of that ID, and builds questions with `substitute: {note, replaces: str(line key)}`. It replaces `memory["pending"]` and returns notes plus `next_choice`.
- `next_choice` renders a substitute question as “<note> Would one of these do?” with “add it to your cart instead” or “replace it in your cart”, and a Skip row of “Don’t add a substitute” or “Leave your cart as it is”. `_choose` calls `add_products` directly (`_receipt` is now `add_products` + `_said`). For a `replaces` item it then calls `CheckoutFlow.remove_line`, but only when the add had no error and the product was added or already present. `_skip` of a replace item says the line stays, marked unavailable.
- `CheckoutFlow.substitutes` (default `None`; `Conversation.__init__` sets it to `tools.cart_substitutes`) enables the `find_substitutes` navigation button in a blocked review (Find substitutes · Remove unavailable · Keep shopping; Empty cart only when fewer than three), the blocker wording and the CART hint. `unavailable_lines(state, memory)` returns `{key, quantity, product: {id, name, brand, category}}` from the cart plus `memory["cart_products"]`. `remove_line(state, key, name)` re-reads the cart and removes that one line if still present.
- `Conversation`: `SUBSTITUTE_COMMANDS` (“find substitutes”, “substitutes”, “find alternatives”, …) route to `cart_substitutes` inside the main try block (so commerce errors and memory saving behave as for other actions); `_last_action` `substitutes` gives View cart · Checkout · Keep shopping.

### Gotchas

- Order-based history items have `category: None`, so a bought-before product the search didn't return is looked up only when its name passes the noun rule. Chat-placed orders keep the listing's category through `cart_products`.
- The noun rule is deliberately strict: “Coca Cola Zero” (noun `cola`) won't accept “Pepsi Black Zero Sugar” by name; it passes only through the shared “Soft Drinks” category.
- A model-ranked alternative with no known `wanted` category passes on the relevance check alone, as alternatives did before. That keeps vague requests (“snacks”) answerable.
- The replaced line is found again by `(product_uid, item_size)` key; if it has already gone, the reply says so and nothing else is removed. It is removed even if it became available again in between, because the customer tapped Replace.
- The `find_substitutes` button is navigation only (no snapshot check), like `remove_unavailable`; the question it opens and the later tap re-read the cart.
